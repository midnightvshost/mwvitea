Чек-лист скорости сайта и Core Web Vitals

Быстрые страницы удобнее для посетителей и лучше индексируются. Используйте этот чек-лист, чтобы найти медленные места сайта, устранить главные причины и не потерять скорость после запуска.

1. Измеряйте страницы, которые важны

Начните с шаблонов, которые приносят трафик и выручку: главная, товар, категория, услуга и оформление заказа. Идеальная оценка страницы, которую никто не посещает, бесполезна.

  • Используйте данные реальных пользователей из Chrome UX Report или аналитики, чтобы увидеть реальную скорость на мобильных.
  • Используйте инструмент лабораторного тестирования, например PageSpeed Insights или Lighthouse, чтобы найти конкретные причины.
  • Проверяйте одну и ту же страницу несколько раз: сторонние скрипты и кеш могут менять результат.
  • Сравнивайте мобильные и десктопные результаты отдельно и записывайте дату каждого теста.
  • Зафиксируйте базовые значения LCP, INP и CLS до изменения кода.

2. Исправьте изображения и Largest Contentful Paint

Изображения часто составляют самую тяжёлую часть страницы и определяют LCP. Займитесь ими до переписывания кода приложения.

  • Сжимайте фотографии и используйте AVIF или WebP с запасными форматами при необходимости.
  • Указывайте атрибуты width и height, чтобы браузер резервировал место.
  • Отдавайте размер, подходящий для каждого экрана, вместо одного огромного оригинала.
  • Не применяйте lazy-load к главному изображению или фото товара; загружайте их раньше.
  • Используйте CDN или сервис изображений, который автоматически меняет размер и формат.

3. Сократите JavaScript и сторонние скрипты

Каждый тег имеет цену. Аналитика, чаты, баннеры согласия, шрифты и скрипты A/B-тестов конкурируют за один и тот же основной поток.

  • Составьте список всех сторонних скриптов и удалите те, которыми никто не пользуется.
  • Загружайте некритичные скрипты после того, как страница стала интерактивной, или только при необходимости.
  • Разделяйте большие пакеты JavaScript и удаляйте неиспользуемые библиотеки.
  • Проверьте менеджер тегов, чтобы один контейнер не загружал десятки тегов на каждой странице.
  • Тестируйте с ограничением CPU для медленного мобильного, а не только на быстром ноутбуке.

4. Шрифты, CSS и стабильность макета

Текст должен появляться быстро и оставаться на месте. Подмена шрифтов, поздний CSS и реклама могут вызывать заметные сдвиги.

  • Предзагружайте основные файлы шрифтов и используйте font-display: swap.
  • Сокращайте наборы символов и удаляйте неиспользуемые начертания и языки.
  • Встраивайте критический CSS и по возможности откладывайте остальной.
  • Резервируйте место для рекламы, встраиваемых блоков, баннеров и уведомлений о cookie.
  • Не используйте иконочные шрифты, если достаточно небольшого набора SVG.

5. Хостинг, кеширование и TTFB

Быстрый фронтенд не исправит медленный сервер. Проверьте время до первого байта и то, как часто повторные посетители могут использовать кеш.

  • Измеряйте TTFB из регионов, где действительно находятся ваши клиенты.
  • Включите сжатие и CDN для статических файлов.
  • Кешируйте HTML только при наличии безопасного способа сброса кеша.
  • Регулярно проверяйте серверное ПО, плагины и запросы к базе данных.
  • Ищите медленные API-вызовы и цепочки редиректов до того, как страница начнёт отображаться.

6. Тестируйте на реальных устройствах и следите после запуска

Производительность не является разовой оценкой. Новые изображения, скрипты и функции изменят её, если никто не отвечает за показатель.

  • Тестируйте на телефоне среднего класса и медленном соединении.
  • Проверяйте основные шаблоны в приватном окне с чистым кешем.
  • Задайте бюджет производительности для веса страницы и Core Web Vitals.
  • Следите за данными реальных пользователей и получайте оповещения о регрессиях после релизов.
  • Раз в месяц проверяйте самые медленные страницы и сначала устраняйте главную причину.
Начните с самого важного шаблона: улучшение страницы товара или услуги обычно важнее полировки главной.
